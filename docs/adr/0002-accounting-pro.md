# ADR 0002 — تطوير النظام المحاسبي إلى مستوى ERP احترافي

**الحالة:** مُنفَّذ (الواجهة في وضع العرض + migration 0057 مُختبَرة على PostgreSQL 16)
**النطاق:** دور المحاسب — وحدة `apps/web/src/features/accounting` و `supabase/migrations/0057_accounting_pro.sql`

## 1. نتائج تحليل المشروع (قبل التعديل)

| البند          | الموجود                                                                                                                                                                                                                |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| التقنيات       | React 18 + Vite + TypeScript صارم، React Query، Tailwind (هوية navy/gold)، recharts، Zod. الخلفية Supabase (Postgres + RLS + `has_perm`).                                                                              |
| وضع التشغيل    | الموقع يعمل بلا Supabase: كل المحاسبة في الواجهة مخازن تجريبية تولّد الدفتر من الأحداث بنفس منطق دوال قاعدة البيانات.                                                                                                  |
| قاعدة البيانات | `chart_of_accounts`, `accounting_periods`, `journal_entries/lines` (قيد مزدوج بمشغّل توازن مؤجّل)، `invoices`, `bills`, `vendors`, سندات/مصروفات/إشعارات مدينة، `bank_accounts`, `vat_config/returns`, `fixed_assets`. |
| الصلاحيات      | الأدوار العشرة + `role_permissions` + `has_perm(module, action)`؛ المحاسب `accounting: full`.                                                                                                                          |
| مراكز التكلفة  | الفروع الأربعة فقط على مستوى رأس القيد.                                                                                                                                                                                |
| الناقص         | أستاذ عام، ميزان بأرصدة افتتاحية، دورة اعتماد للقيود، قيود عكسية/متكررة، قوائم مصنّفة وتدفقات حقيقية، ذمم بأعمار وكشوف، تسوية بنكية، موازنات، مشاريع، إقفال سنوي، فوترة إلكترونية، تنبيهات، مساعد، سجل تدقيق محاسبي.   |

### أخطاء في سلامة البيانات اكتُشفت وأُصلحت

1. **قائمة المركز المالي غير متوازنة بعد الإهلاك:** مجمع الإهلاك 1290 (دائن الطبيعة) كان يُجمع على الأصول بدل طرحه → الأصول ≠ الالتزامات + حقوق الملكية بفارق ضعف الإهلاك.
2. **مردودات المبيعات 4900 كانت تزيد الإيراد** في لوحة المؤشرات بدل إنقاصه.
3. **قيود الإقفال تُصفّر قائمة دخل الشهر المقفل**، وكانت مؤرخة دائمًا يوم 28 مهما كان طول الشهر.
4. **الفترة المقفلة لا تمنع الترحيل** في وضع العرض (القيود اليدوية والإهلاك).
5. **التحصيلات من شاشة المدفوعات لا تُرحَّل للدفتر** → رصيد ذمم العملاء التفصيلي ≠ حساب الرقابة 1120.
6. **بيانات بذرة غير مرحّلة:** فاتورة مورد مسددة بلا سند صرف (9,000) وأصول ثابتة مسجلة (132,000) بلا قيد شراء.
7. **مصاريف المكاتب الخارجية بلا ضريبة:** تُعرض الآن في بند الاحتساب العكسي (9) في نموذج الإقرار مع تنبيه لمراجعة مستشار ضريبي — **لم يُغيَّر الترحيل** لأنه قرار ضريبي يحتاج اعتمادًا.

> أثر 6 على الأرقام المعروضة (موثّق): النقدية 249,795 ← 104,595 (شراء الأصول + سداد المورد + حملة رمضان التجريبية)، والمصروفات +4,200 (قيد حملة رمضان). الإيراد دون تغيير.

## 2. القرار — أعدنا استخدام الموجود وأضفنا فوقه

- **أُعيد استخدام:** `journal_entries/lines`، `has_perm`، `app_config` (كل العتبات الجديدة منه وتُعدَّل من الإعدادات)، `salesLedger` (فواتير العملاء)، `bills`، `bank_accounts`، `fixed_assets`، مكوّنات `shared/ui` (أُضيف لـ Table فرز ولـ Modal أحجام — توافقيًا)، `sar/dateAr`.
- **الأدوار العشرة بلا تغيير.** الصلاحيات الدقيقة (المدير المالي، المحاسب العام، محاسب العملاء، محاسب الموردين، المراجع الداخلي، مستخدم التقارير) **ملفات مهام** تحت الدور: `has_acc_perm(area, action)`.
- **الحساب بالهللة** (`data/money.ts`) — لا جمع أعداد عشرية؛ مطابق لـ `numeric(14,2)`.
- **الدفتر مستمر**: لا يُعاد ترحيل الأرصدة الافتتاحية (لتجنب الازدواج)؛ قيد إقفال السنة ينقل الربح إلى 3200.

## 3. ما بُني (13 مجموعة في القائمة)

لوحة مالية تفاعلية (20 مؤشرًا + 8 رسوم + فلترة تاريخ/فرع/مركز تكلفة + آخر تحديث + Excel/PDF) · مركز تنبيهات بمسؤول وأولوية وحالة · إشعارات دائنة · أستاذ عام برصيد تراكمي وفتح القيد الأصلي · ميزان مراجعة (افتتاحي/حركة/ختامي، رئيسي/فرعي، مقارنة) · قيود بدورة مسودة ← اعتماد ← ترحيل، فصل مهام، قيود عكسية ومتكررة وافتتاحية وتصحيحية ومرفقات · قوائم مالية مصنّفة مع مقارنة وانتقال للحسابات والقيود وسياسات محاسبية مكتوبة · ذمم عملاء/موردين بأعمار وحدود ائتمان وكشوف وتحصيل جزئي وتذكيرات وجدولة دفعات ومطابقة مع حساب الرقابة · تسوية بنكية (استيراد CSV، اقتراح مطابقات، تقرير تسوية، قواعد معتمدة تنشئ مسودات فقط) · أصول (قسط ثابت/متناقص، جدول إهلاك، بيع واستبعاد بربح/خسارة، نقل بين الفروع) · مراكز تكلفة (أقسام/مشاريع) وتوزيع المصروفات المشتركة وموازنات بتنبيهات تجاوز · نموذج إقرار VAT بترتيب بنود الهيئة · إقفال شهري بقائمة تحقق وسنوي وإعادة فتح بسبب · مساعد محاسبي · ملفات مهام وسجل تدقيق.

## 4. الفوترة الإلكترونية (ZATCA) — المكتمل مقابل ما يحتاج اعتمادًا

| مكتمل داخل النظام                                         | يحتاج اعتمادًا/تكاملًا رسميًا                     |
| --------------------------------------------------------- | ------------------------------------------------- |
| QR بصيغة TLV (المرحلة الأولى) + فحص الحقول الإلزامية      | رسم رمز QR كصورة على الفاتورة المطبوعة (مكتبة QR) |
| منع تعديل الفاتورة والتصحيح بإشعار                        | التسجيل في منصة «فاتورة» والحصول على CSID         |
| XML بهيكل UBL 2.1، عدّاد ICV، سلسلة PIH، تجزئة SHA-256    | التطبيع C14N والتوقيع XAdES وفحص المطابقة         |
| حالات الإرسال (مولّدة/بالانتظار/مجازة/مُبلَّغ/مرفوضة/خطأ) | استدعاء واجهات Clearance/Reporting                |

**لا يُعدّ النظام متوافقًا رسميًا.** المرجع: zatca.gov.sa. (migration 0028 كان قد أزال أعمدة ZATCA من `invoices`؛ أُعيد إدخال البيانات في جدول مستقل `einvoice_documents` محمي من التعديل.)

## 5. المساعد المحاسبي

محرك محلي حتمي يفهم الأسئلة العربية الشائعة، يجيب من البيانات المصرّح بها فقط مع الفترة والمصدر ودرجة الثقة والافتراضات، يرفض أي طلب ترحيل/تعديل، ويسجّل كل سؤال. **لا يوجد مزوّد ذكاء اصطناعي مهيأ** — البنية جاهزة (`ai_provider_config` بلا مفاتيح؛ المفتاح في Vault/Edge Function) ولا تُرسل بيانات للخارج.

## 6. النسخ الاحتياطي والاستعادة (قبل تطبيق 0057 على الإنتاج)

```bash
pg_dump --format=custom --file=before_0057.dump "$DATABASE_URL"   # 1) نسخة كاملة
supabase db push                                                  # 2) تطبيق 0057
# استعادة كاملة عند الحاجة:
pg_restore --clean --if-exists --dbname="$DATABASE_URL" before_0057.dump
# أو تراجع جراحي (يُبقي القيود المرحّلة وسجل التدقيق):
psql "$DATABASE_URL" -f supabase/rollback/0057_accounting_pro_down.sql
```

تم التحقق محليًا على PostgreSQL 16: تطبيق 0001→0057 ثم التراجع ثم إعادة التطبيق بنجاح، واختبار وظيفي للدوال (رفض غير المتوازن، فصل المهام، حماية المرحّل من التعديل/الحذف، القيد العكسي، منع الترحيل في فترة مقفلة، إعادة الفتح بسبب، منع تعديل سجل التدقيق، توازن `trial_balance`).

## 7. المتبقي / خارج النطاق الحالي

- ربط شاشات المحاسبة بـ Supabase الفعلي (حاليًا وضع عرض كبقية النظام؛ الدوال والجداول جاهزة).
- رسم QR كصورة، والتكامل الرسمي مع «فاتورة».
- إرسال التذكيرات فعليًا (مزوّد SMS/واتساب) — حاليًا تُضاف لقائمة الإرسال.
- رفع المرفقات إلى Supabase Storage (الواجهة تحفظ بيانات الملف في وضع العرض).
- الوضع الليلي: غير مدعوم في بنية المشروع (لا `darkMode` في Tailwind) — لم يُضف.
- النظام شركة واحدة؛ لا يوجد تعدد شركات لعزله.
